# Orientation Module — CONTEXT.md

## Purpose
"What to do next" screen at `/app/orientation`. Presents the seven Maqasid pillars as domain cards — the weakest domain (by the tier-gated engine) is flagged and fronted on entry. Each card leads with the pillar's **static one-line description** (what the domain *is*, values-layer aware, from `getPillarDescription`) and then shows the current **task** title under NOW. The current *step* (the first non-satisfied subtask of that task — see **Sequential locking** below) is no longer on the face; it lives in the sheet. **One layout at every width** (2026-07-27): a horizontal scroll-snap carousel, one card centred with both neighbours peeking, plus a dot row that doubles as jump nav. The desktop stage-plus-side-rail spread (`OrientationSpread`) was retired in the same change. Tapping/clicking the fronted card opens the **sheet**: the current step shown within its ordered task/subtask chain via a **Task stepper** (numbered pills, >1 task) + **Subtask stepper** (lettered chips, >1 subtask) — every step is visible, only the true current one is actionable, and locked steps ahead are previewable — plus grounding evidence, Why/How, and three non-punitive exits (Mark done / Doesn't apply / Not now). Never shows a flat task list; depth lives in the sheet, breadth is one swipe (or rail click) away.

## Architecture
```
Orientation (container)
├── header            — eyebrow / title / one-line intent (no streak/date/greeting)
├── OrientationCarousel        — unconditional, every width
│   ├── OrientationCard × 7    — one <button> each, onOpen(pillarId)
│   │       face = pillar name + description + NOW <task title> + bar
│   └── dot row × 7            — click = centre that card (jump nav; never opens the sheet)
└── OrientationSheet (portal, only when a card is open; chrome + empty state only)
    └── shared/SequentialStepFlow — owns `preview` = {taskIndex, subtaskIndex} + render-time reset
        ├── OrientationSteppers → TaskStepper / SubtaskStepper — built here, passed down as slots ↓
        ├── shared/SubtaskStepDetail — crumb / [taskStepper] / title+prog / tags /
        │   [subtaskStepper] / Now box / Why & how accordion / shared/SubtaskEvidence (lazy SubtaskSources)
        │       (body shows the *previewed* task/subtask; falls back to the current step)
        └── OrientationActions   — 3 buttons; primary pinned to the true current step, or an
                                   enabled "Completed" (revert) when browsing a done step behind
```

## Key Patterns
- **Sequential locking (the model).** A domain (pillar) holds an ordered list of tasks; each task an ordered list of subtasks. Sequence is **curated seed order** — `deriveBoardSequence` runs `tasksByProject[boardId]` through `orderBoardTasks` (sort by `task.seedOrder`, else `1e6 + (order ?? index)` so user-created tasks land after the whole curated chain), and `task.n` is a display label only, never read for ordering. The **current task** is the first non-complete task in that order (complete ⇔ every subtask `isSubtaskSatisfied`, i.e. done || notApplicable); the **current subtask** is its first non-satisfied step. Everything is visible; only the true current step is actionable — anything after it is *locked* (previewable, not actionable). A task is **snoozed today** when `snoozedUntilDayKey === todayKey`, which makes its board non-actionable; selection then walks to a sibling board and, failing that, the pillar-ranking loop falls through to the next pillar (tier triage preserved). All of this derivation lives in the pure selector (`deriveBoardSequence` / `deriveSubtaskSteps` / `findActiveBoardInPillarTier`) — this folder only renders it.
- **Recompute is effect-driven, not handler-driven.** Actions (Mark done / Doesn't apply / Not today) do NOT call the selector directly — they mutate the store and let the `useEffect` (on `[projects, tasksByProject, maghribRaw]`) rebuild the carousel. This avoids a stale-closure race where a handler-computed model would use a `tasksByProject` snapshot taken before React re-renders. There is no `tick`/override ref anymore — the **carousel itself is the pillar picker**, so a "switch domains" action isn't needed (it's a swipe).
- **Held-task continuity is sheet-level, reconciled three ways.** The open sheet is keyed by `openPillarId`, not by a task ref. After an action, `pendingRef` carries the acted `{pillarId, taskId, ackSame, ackAdvance, ackClose}` across the store-driven recompute; the effect reconciles it against the rebuilt card. **Still actionable + same task** (`card.task.id === pending.taskId`) ⇒ the sheet stays open and advances to the next subtask (`ackSame`, e.g. "Marked done."). **Still actionable + different task** (the current task cleared or was set aside and the board rolled to its next task — same board or a sibling in the pillar) ⇒ the sheet stays open on the new task (`ackAdvance`, e.g. "Task complete."). **Not actionable** (board complete, or the task was snoozed and no sibling board qualifies) ⇒ close the sheet, set `focusPillarId = recommendedPillarId` to re-front whatever is now weakest, show `ackClose`. Selection is stable across recompute because `findActiveBoardInPillarTier` re-picks the first actionable board in the pillar+tier while it still has eligible work.
- **`dayKeyRef` = the Islamic-day key the current model was built for.** The effect writes it (`computeTodayKey(maghribRaw)`) and feeds it to `buildOrientationCarousel`; `handleNotToday` reads it so the **task-level** snooze (`updateTask(project.id, task.id, { snoozedUntilDayKey })`) targets the day the user is looking at, not a freshly-recomputed key if Maghrib rolled over between render and tap. Routing the wall-clock value through this ref also keeps the effect's `setModel` clear of `react-hooks/set-state-in-effect` (the value depends on an opaque ref read, not purely on reactive deps — the same shape the rest of the codebase uses).
- **`computeTodayKey` reads the wall clock**, so it is only ever called inside effects/handlers, never the render body (`react-hooks/purity`).
- **One layout at every width — the carousel is unconditional (2026-07-27).** There is no `useMobile()` gate and no CSS layout switch: `Orientation.jsx` always mounts `OrientationCarousel`, and the whole responsive story is a 620px column cap plus ONE `@container orient (min-width: 480px)` block that re-shows the native scrollbar (mouse users get a scroll affordance; touch keeps a clean track — the same call `KanbanBoard.css` makes) and bumps type. It is a **container** query, not a media query — see the gotcha below; that distinction is load-bearing. The scroll-snap JS (`centerEl`/`nearestIndex`) is bounding-rect arithmetic with no width assumptions, so it is correct at every width by construction (measured: every card centres to 0px offset bar the two at the scroll extremes, which sit ±28px off by definition). `focusPillarId` survives the spread's removal — the container still writes `setFocusPillarId(recommendedPillarId)` on task-complete and the carousel re-centres smoothly on it.
- **The card face answers "what is this domain" before "what is open in it".** The description is static (values-layer aware, never board-derived) and therefore renders **outside** the three-way `hasEligible`/`seeded` branch — it is the one line that must survive "Nothing left for today" and "No steps yet" too. Under NOW the face shows the **task** title, not the subtask: the task is the unit with a beginning and an end, and the subtask was duplicating exactly what the sheet opens to. Copy lives in `src/data/maqasid.js`, never inline here.
- **Sheet chrome is reused, not rebuilt.** `OrientationSheet` uses the shared `pp-slideup__*` classes (`createPortal` to body, backdrop button, `role="dialog"` + `aria-modal`) and `useFocusTrap(active, onClose)` for focus trap + Escape + focus restore — the same pattern as `ProjectSlideUp.jsx` / `NodePhaseSlideUp.jsx`.
- **Step internals are shared, not local.** The sheet body renders `shared/SubtaskStepDetail` (crumb / title+prog / tags / Now / Why & how / Evidence) — the same component the Prophetic Path node popup drill-in uses. Evidence is `shared/SubtaskEvidence` (formerly `OrientationEvidence.jsx` here), which lazy-imports `work/SubtaskSources.jsx` exactly like `TaskDetailPanel.jsx`; "Why & how" keeps TaskDetailPanel's markdown precedence (why/how → description → empty note). Class names keep the historical `os-sheet__` / `orient-evidence__` prefixes.
- **Browse-ahead preview lives in `shared/SequentialStepFlow` and is reset during render (never in an effect).** The shared component (extracted from this sheet 2026-07-27; also hosts the Prophetic Path node-popup steppers) owns `preview = {taskIndex, subtaskIndex}` so the operator can click a locked step to read it; the body then renders the *previewed* task/subtask (`SubtaskStepDetail` receives `previewedTask`/`previewedSubtask`, not the card's current step). It resyncs to the true current step via React's "adjust state during render" pattern — a `syncedTo` string key derived from the host's `resetKey` + current indices; when the card advances the key changes and `setPreview(...)` runs **in the render body**, before paint. It is deliberately **not** a `useEffect`/`useLayoutEffect`: a synchronous `setState` inside an effect trips `react-hooks/set-state-in-effect` and flashes the stale step. The previewed subtask index is **clamped** into `[0, stepCount-1]` so a stale index from a longer previous task can't overrun a shorter one. Actions stay pinned to the true current step for the ahead case (`Complete prior steps`, disabled); browsing **behind** shows the primary as `Completed` — **enabled** — and clicking it calls `onRevert(previewedTask, previewedSubtask)` to un-complete that step (un-toggles `done`, or clears `notApplicable`), with the secondaries disabled. The host's `handleRevert` (`Orientation.jsx`) acks "Step reopened."; the model recompute + `syncedTo` reset snaps current back to the reopened step automatically.
- **Grounding helpers** (`isSubtaskGrounded`/`deriveSubtaskTier`) live in `src/utils/subtask-grounding.js`, shared with `TaskDetailPanel.jsx` — do not reimplement locally.

## Gotchas
- **`.orient-carousel`'s top padding (`var(--space-3)`) exists to contain the `__flag` overhang.** The badge sits at `top:-9px` (+1px border) above the card, and because the track sets `overflow-x:auto`, the CSS spec forces `overflow-y` to computed `auto` — anything above the scrollport is CLIPPED. Shrinking that padding below ~10px re-clips the "Weakest — recommended" badge.
- **The card width is a percentage OF A PERCENTAGE — never swap it for a px basis.** `.orient-carousel` has `padding: … 11% …`, so its content box is 0.78 × the page column; `.orient-card { flex: 0 0 78% }` then resolves against *that*, making the card ~60.8% of the column at every width. That is why the layout cannot overflow — verified by simulating page columns from 200px to 620px: no overflow at any of them. A px `flex-basis` does overflow at the narrow end.
- **The responsive block is a CONTAINER query on `.orient-page`, not a media query — do not "simplify" it back.** `min-width` measures the **viewport**; the real constraint is the app-shell content column. Sidebar expanded (248px) + Islamic panel open (280px) take ~470px, so an 800px *viewport* can leave this page a ~285px *column* — narrower than a 390px phone. The first cut of this page used `@media (min-width: 768px)` and was measured doing exactly the wrong thing there: all seven descriptions truncated and six of seven task titles truncated, i.e. strictly worse than the phone the rule was meant to improve on. `.orient-page` therefore sets `container-type: inline-size; container-name: orient` and the type/scrollbar block queries `@container orient (min-width: 480px)`. Threshold is against the container's **content box**, so a 390px phone (~358px) stays on the small scale and a capped 620px column (~588px) gets the large one.
- **`.orient-carousel`'s `scroll-padding-inline` only has to stay *symmetric*.** Under `scroll-snap-align: center` a symmetric value cancels out entirely, so 11% is correct at any card width and needs no media-query counterpart. `centerEl`'s bounding-rect math agrees with it automatically.
- **`.orient-card` uses `min-height`, not `height`.** The track is a flex line, so all seven cards stretch to the tallest — that is what keeps them flush while the description's line count varies by pillar. Restoring a fixed `height` re-introduces clipping on the longest description (faith, 138 chars).
- **No `position: fixed` in this module's own CSS.** The sheet's fixed overlay comes from the SHARED `.pp-slideup__root` chrome (every app slide-up reuses it — it is modal overlay chrome, not page/nav layout). `OrientationSheet.css` adds no new `position:fixed`. The "no position:fixed" rule targets page and `MobileNav` chrome (see project memory), not modal overlays.
- `OrientationSheet.css` is imported AFTER `ProjectSlideUp.css`; its `.os-sheet__panel { max-width: 520px }` narrows the shared centered panel by source order at equal specificity (same trick `NodePhaseSlideUp.css` relies on). Keep that import order. Height/centring come entirely from the shared chrome now.
- `shared/SubtaskEvidence.jsx` imports `../work/TaskDetailPanel.css` for the `tdp-*` classes `SubtaskSources` renders into — a known cross-folder wart, accepted as-is; a future cleanup could relocate `SubtaskSources` + its CSS to `shared/`.
- `timeToMs`/`localDayKey` are module-private in `src/utils/islamic-day-key.js`; only `computeTodayKey` is exported. (`usePrayerTimes.js` and `PropheticPath.jsx` still carry their own `timeToMs` copies — pre-existing duplication, untouched.)
- Do NOT add a 4th tile to `MobileNav.jsx` for discovery — its 3-tile bar is intentionally reserved. Discovery is via `Sidebar.jsx` (and the app-home handoff), not a nav tile.
- Streak counter + "welcome back" banner are deliberately deferred (conflict with the locked "no streak/guilt mechanic" decision) — do not add them without revisiting that decision.
- **Sequencing reads `seedOrder` (via `orderBoardTasks`), never `task.n`.** `n` is a display label only. The chain order comes from the curated `seq` on the seed task, persisted as `seedOrder` and **reconciled on every boot** by `backfillAndStripSeeds` — so re-ordering a board is a seed-file edit, not a storage edit (**all 108 boards curated** — 28 core + 62 growth/excellence hand-authored, see [2026-07-27-milos-seed-order-curation](wiki/decisions/2026-07-27-milos-seed-order-curation.md), plus the 18 generated prayer boards, see [2026-07-27-milos-prayer-board-ordering](wiki/decisions/2026-07-27-milos-prayer-board-ordering.md)). Note `decorateTaskChain` is deliberately **not** sorted — but that is true **only for the merged cross-project pool** (the Prophetic Path node popup's non-prayer branch), where `seedOrder` is meaningless across boards. **A caller that owns a single board must pass it through `orderBoardTasks` first.** The popup's prayer branch (`buildPrayerPhaseTasks`) reads exactly one `prayer_{id}_{phase}` board and did **not** sort until 2026-07-27, so the prayer stepper rendered in raw `localStorage` order — reading "does not sort" as a blanket rule is how that was missed. `NodePhaseSlideUp`'s `buildSubmoduleStudyTasks` (Education tab, 2026-07-28) is the same shape: it unions three *whole* boards (core/growth/excellence for one submodule) rather than a keyword-filtered slice, so — like the prayer branch, unlike `buildTasksForNode`'s non-prayer pool — each board is run through `orderBoardTasks` individually before concatenation, since seed order **is** the curriculum order here.
- **`orderBoardTasks` is the ONE task comparator — the chain and the boards can no longer diverge.**
  It lives in [orientation-selector.js](../../data/orientation-selector.js) and is now imported by
  every board surface too (KanbanBoard, ListView, StageSidebar, PillarLevelDashboard, ProjectBoard,
  BbosTaskPanel) as well as `deriveBoardSequence`. Key = `seedOrder`, else `1e6 + (order ?? index)`,
  so **user-created tasks sort after the whole curated chain**. The ad-hoc `seedOrder ?? order`
  copies the boards used to carry put them *before* it, so a board and its chain disagreed — see
  [2026-07-27-milos-board-order-single-authority](../../../wiki/decisions/2026-07-27-milos-board-order-single-authority.md).
  Never re-inline a comparator here.
- **Adding a subtask to a seed task re-opens that task in the chain.** `isTaskComplete` is pure
  `subtasks.every(satisfied)` — it has no memory of `completedAt` — so growing a finished task's
  array makes it the current step again. Intended (a new obligation *is* outstanding work), but it
  means a seed content edit can silently reactivate a board the operator had finished. New seed
  subtasks reach already-seeded boards via `backfillAndStripSeeds`, which **appends at the end**; if
  position matters, the seed edit needs a one-shot insertion migration — see `alignSubtaskOrder` in
  [migration.js](../../services/migration.js) and
  [2026-07-27-milos-subtask-foldin](../../../wiki/decisions/2026-07-27-milos-subtask-foldin.md).
- **Two different "not now"s. Keep them apart.** *Task-level* `snoozedUntilDayKey` is what
  Orientation's own footer writes (`updateTask`): it drops the whole **board** out via
  `deriveBoardSequence`'s `actionable` flag, and the cross-pillar/cross-board fall-through depends
  on that. *Subtask-level* `snoozedUntilDayKey` is what the Prophetic Path popup writes
  (`updateSubtask`): it advances the chain past the step, and — since 2026-08-13 — past the whole
  task once nothing eligible is left in it.
- **The `snoozed` task-pill state is no longer latent — but only where `todayKey` is passed.**
  Under the cross-board fall-through rule a *task-snoozed* board is skipped and never surfaced, so
  that route to `TaskStepper`'s moon glyph stays unreachable; do **not** "fix" it by surfacing
  snoozed boards, which would weaken the lock invariant. The glyph is now reached by the *other*
  route: `findCurrentTaskIndex` / `decorateTaskChain` / `taskPillState` each take an optional
  trailing `todayKey` and treat a task with real work but no eligible subtask today as **settled**
  (`isTaskSettledToday` = `isTaskComplete || isTaskDeferredToday`), rolling the chain forward and
  painting the rolled-past pill amber. `taskPillState` must check deferred **before** the
  positional `index < currentTaskIndex → done` rule, exactly as `subtaskChipState` does, or the
  rolled-past task reads green. `isTaskComplete` stays the honest "all satisfied" verdict and
  `getPillarTierSubtaskStats` still counts off `isSubtaskSatisfied` alone, so a deferred task can
  never inflate a progress ratio. All of it is live **only in the Prophetic Path node popup**
  (`NodePhaseSlideUp` passes `todayKey`); this module's `SequentialStepFlow` call omits it, and a
  falsy `todayKey` reduces every one of these helpers to its previous behavior byte-for-byte. Do
  not thread `todayKey` through `Orientation.jsx`'s call without re-deciding the carousel
  fall-through question first — see the flagged gap below and
  [2026-08-13-milos-task-deferral-roll-forward](../../../wiki/decisions/2026-08-13-milos-task-deferral-roll-forward.md).
- **Do not convert `SequentialStepFlow`'s `preview` reset into a `useEffect`.** It is a render-time `setState` guarded by the `syncedTo` key (see Key Patterns) — an effect version trips `react-hooks/set-state-in-effect` and flashes the stale step for one frame. (The reset moved with the extraction — it now lives in `src/components/shared/SequentialStepFlow.jsx`, not the sheet.)
